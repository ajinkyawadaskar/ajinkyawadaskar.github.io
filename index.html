Credit Decision Explainer
When a bank denies your loan, US law requires the specific reasons. Hand the model's output to an LLM and it writes fluent reasons that aren't true — one draft denied an applicant for "limited employment history and recent credit inquiries." Neither was a factor; one isn't even in the dataset. So reasons are chosen by plain code from real SHAP attributions, the LLM only words them, and a validator checks every sentence before it ships.

The finding I didn't expect: the model wanted to deny people for paying their bills on time. Mathematically correct — that group defaulted 57% of the time — and unusable in a letter. Traceable to real evidence isn't enough; it also has to be a reason you're allowed to give.

Data Analyst Agent
Ask a question in plain English, get an answer from BigQuery. Every model writes competent SQL now — the part nobody demos is what happens when it writes something wrong. Inventing a column, reaching for a table you never exposed, scanning six gigabytes because it forgot a date filter. So every generated query is parsed and checked against five rules that don't depend on the model cooperating: statement type on the syntax tree, table allowlist, column existence, row cap, and a dry-run cost ceiling. Fail one and it doesn't run.

The cost check was the interesting one. COUNT(*) across 366 tables costs nothing — BigQuery answers from metadata — while one unfiltered SELECT * is 5.8 GB. "Touches many tables" and "expensive" are different questions, and a guard built on the wrong one blocks free queries while letting costly ones through.
