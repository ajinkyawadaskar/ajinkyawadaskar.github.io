LLM-Powered ETL Migration Agent

How I approached translating legacy Alteryx ETL workflows into production BigQuery SQL and Dataform DAGs at Ford Motor Company.

// the approach

Ford was modernizing off a legacy analytics stack. Hundreds of Alteryx workflows — visual, drag-and-drop ETL — needed to become BigQuery SQL and Dataform DAGs. Manual translation was the default: open each workflow, reverse-engineer the logic, rewrite it. At the scale of the backlog, that was a multi-year effort.

I built an agentic pipeline using LangChain + GPT-4 that automated the bulk of the translation. The agent parsed Alteryx workflow definitions, identified transformation patterns (joins, filters, aggregations, formulas), and generated equivalent BigQuery SQL. It also produced Dataform dependency graphs so the migrated pipelines slotted into the existing orchestration layer.

// what was automated vs. what wasn't

The LLM handled well:

  • Standard transformations — joins, filters, aggregations, column renames, type casts
  • Formula translation from Alteryx expression syntax to BigQuery SQL functions
  • Dependency graph construction — identifying upstream/downstream relationships for Dataform DAGs
  • Boilerplate generation — table definitions, incremental configs, assertion stubs

What still required human judgment:

  • Complex business logic embedded in workflow annotations or naming conventions that varied by author
  • Edge cases in date handling and type coercion where Alteryx and BigQuery disagree on defaults
  • Semantic equivalence validation — the generated SQL could be syntactically correct but logically different
  • Stakeholder sign-off on whether a transformation was still needed or could be simplified during migration
// why an LLM instead of a rule-based transpiler

Alteryx workflows encode logic visually with implicit conventions that vary by author. Two analysts might implement the same transformation in structurally different ways — different tool ordering, different intermediate steps, different formula styles. A rule-based transpiler would need to handle every variant explicitly.

The LLM generalizes across patterns while the human validates the output. This is the same "LLM as draft, human as validator" pattern I used in the portfolio projects, applied at a different scale.

Result: ~80% of manual migration effort eliminated. The remaining 20% was the judgment-heavy work that needed a human regardless.

This was proprietary work at Ford Motor Company. I can describe the approach, methodology, and architecture patterns, but cannot share code, internal data, or specific pipeline details.
