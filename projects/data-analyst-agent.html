Guardrailed Natural Language to SQL Agent

Natural language to SQL over BigQuery — with a guardrail layer that parses every generated query and decides whether it's allowed to run at all.

Try the Demo GitHub Live API
// the problem

Getting an LLM to write SQL is easy. Every model does it competently now.

The part nobody demos is what happens when it writes something wrong — and "wrong" has a wide range. It can invent a column that doesn't exist. It can reach for a table you never meant to expose. It can write a perfectly valid query that scans six gigabytes because it forgot a date filter. Or it can write DROP TABLE at the end of something that looked fine.

You can ask a model nicely not to do those things. That lowers the rate. It doesn't bound it. This project is the other half: parse every generated query before it runs, check it against rules that don't depend on the model cooperating, and refuse the ones that fail.

// architecture

The system has two paths. A structured path compiles SQL from a certified glossary — the LLM never writes a query. An unstructured path retrieves support notes from a vector store. A router decides which path (or both) a question needs, and a synthesis layer merges the results.

Each layer, what it does, and how it scales

Router. Regex classifier that looks at question shape — does it ask for a number, a note, or both? Free, instant, and every decision traces to the exact pattern that fired. Production: swap for a lightweight LLM classifier when questions get ambiguous enough that keywords miss.

Intent Extraction. The LLM reads the question and emits a small JSON naming a certified measure, dimensions, and filters — validated against semantic_model.yaml. If the metric doesn't exist in the glossary, it's refused. The LLM never writes SQL. Production: expand the glossary as new metrics get certified; the compiler handles the rest.

Semantic Cache. SHA-256 of the resolved intent + caller identity. Two differently worded but identical questions hit the same entry. Two callers never share a filtered result. 74–89% latency reduction on hits. Production: move from SQLite to Redis; add TTL-based invalidation tied to data freshness.

Semantic Compiler. sqlglot expression builders turn the validated intent into SQL — graph traversal for joins, AST construction for predicates. No string concatenation anywhere. Production: add more join paths and aggregate functions to the semantic model as the warehouse grows.

Security Injection. After the LLM is done contributing anything, code walks the compiled AST and ANDs row-level predicates onto tables that carry a policy. An invalid identity raises an error outright — never a query that quietly returns zero rows. Production: wire to a real IAM provider instead of simulated tenant identities.

BigQuery Execution. The compiled, security-injected query runs against live BigQuery with the same guardrails as the original agent (cost ceiling, row cap). Production: add query queuing and priority lanes for expensive scans.

Vector Search (RAG path). For unstructured questions, retrieves relevant support notes from a LanceDB vector store. For stacked questions ("find customers who complained about billing, then show their revenue"), retrieval resolves who, then the compiler builds a precise query scoped to exactly those IDs. Production: replace synthetic notes with a real support-ticket corpus; add reranking.

Synthesis Layer. Merges outputs from the structured and unstructured paths into one attributed response. The LLM words the answer; the data behind it is deterministic. Production: add citation links back to source notes and query results.

Audit Envelope. Every response ships with a trust receipt — compiled SQL, proven join path, cache hit/miss, retrieved note IDs, route taken, and latency. A caller never has to take "trust me" as the only option. Production: pipe into a compliance dashboard for audit trails.

MCP Server. The gateway is exposed as a Model Context Protocol tool via FastMCP. Any MCP-aware client — not just this agent's UI — can call it through the same compile → security → guard → execute pipeline. Production: register as a standard tool in the organization's MCP registry.

Observability. OpenTelemetry spans on every layer, exported to Langfuse. init_tracing() with no keys is a documented no-op — spans are created, just not exported. Production: swap Langfuse for Datadog or your existing APM; it's a config change, not a code change.

// the hardest decision

Why AST parsing instead of regex or a prompt instruction

A prompt instruction ("never write DELETE") reduces the rate of bad SQL. It doesn't bound it — the model can still produce whatever it wants.

A regex can be fooled by comments, string literals, or CTEs. DELETE inside a comment is harmless; DELETE inside a CTE is not. A regex can't tell the difference.

An AST parse with sqlglot sees the actual statement type regardless of how it's formatted — DELETE buried inside a CTE gets caught because the parser sees a Delete node, not because a pattern matched a string. The check is on the structure, not the text, which is what makes it a bound rather than a rate reduction.

// numbers

Schema compression — the first win was noticing the schema was duplicated, not the clever part.

Google Analytics stores each day as its own table — 366 of them, every one with the same 338 columns. Describing all of that comes to 1,235,616 tokens. BigQuery already treats those tables as one thing via a wildcard, so describing one shard drops the whole corpus to 3,921 tokens. 315x smaller, nothing lost.

Cost ceiling — dry-run measurements, not estimates.

QueryBytesResult
SELECT * all GA shards, no date filter5.767 GBblocked

COUNT(*) across every shard is free — BigQuery answers it from metadata. A guard that counted tables instead of bytes would block a query that costs nothing. Bytes is the right signal.

// what didn't work

A guardrail that failed open

Column validation looked up each table's columns from the schema context. If the lookup came back empty, the code treated that as "I don't know this table" and skipped the check.

The lookup was broken — wrong data structure, so it came back empty every time. Column validation silently never ran, and a query selecting a column that doesn't exist passed all four checks and reported clean.

The bug was a one-liner. The lesson wasn't. A guardrail that skips when it's confused is worse than one that doesn't exist, because it reports success. Any check that can't complete has to fail closed.

// what shipped next: semantic execution gateway

The guardrail layer above catches bad SQL after the LLM writes it. The semantic execution gateway flips the model: the LLM never writes SQL at all. It picks a metric off a small certified list, and a deterministic compiler turns that into a query. An off-model question doesn't produce a plausible wrong answer — it fails to compile.

This is on the feature/semantic-gateway branch, tested against live BigQuery and a live Gemini model. Not merged to main yet.
