Governed Text-to-SQL Agent with a Semantic Execution Gateway

Ask a question in plain English, get an answer backed by real data. The LLM never writes SQL — a deterministic compiler does. If the question doesn't map to a certified metric, it fails to compile instead of guessing.

Try the Demo GitHub Live API
// the problem

Most text-to-SQL tools let the LLM write the query directly. That works until it doesn't — and the failure mode is uniquely dangerous. The model doesn't crash or throw an error. It returns a number that looks right, reads right, and is completely wrong. A made-up column, a missing join, a filter that silently drops half the data. You get a confident answer with no way to know it's broken.

The first version of this project added guardrails — AST parsing, table allowlists, cost ceilings — to catch bad SQL after the model writes it. That works, but it's still reactive. The semantic execution gateway takes a different approach: don't let the LLM write SQL at all. It picks a metric from a certified list, and deterministic code compiles the query. A hallucinated metric becomes a name that doesn't resolve, not a query that runs and returns something plausible.

// how it works

You ask a question in plain English. The system figures out what kind of answer you need and builds it from verified components — no free-form SQL generation anywhere in the pipeline.

The structured path — when you ask for a number

"What's the total revenue for ACME last quarter?" The LLM reads your question and outputs a small JSON — just the metric name, dimensions, and filters. That JSON is validated against a semantic_model.yaml glossary where every measure, dimension, and join is pre-certified. If the metric exists, a compiler (sqlglot, no string concatenation) builds the SQL. If it doesn't, the request is refused — not answered with a guess.

Before the query runs, a security layer walks the compiled AST and injects row-level filters based on the caller's identity. The LLM never sees these filters, can't modify them, and can't skip them. Then the query hits BigQuery with the same cost ceiling and row cap from the original guardrail layer.

The unstructured path — when you ask about context

"What were customers complaining about last month?" There's no metric to compile here. The system retrieves relevant support notes from a LanceDB vector store and surfaces them with attribution — which notes matched and why.

Stacked queries — when you need both

"Find customers who complained about billing, then show their revenue." The retrieval path finds who from the notes, then the compiler builds a precise SQL query scoped to exactly those customer IDs. The LLM decides what to compute; the code decides how to scope it. This split took three prompt iterations to get right — the key was explicitly forbidding the model from trying to identify accounts on its own.

The router

A regex classifier looks at question shape and decides which path — structured, unstructured, or both. It's free, instant, and every decision traces to the exact pattern that fired. Its blind spot is exactly what you'd expect: a stacking case that says "had trouble" instead of "complained" routes structured-only and drops the qualitative half. Logged, not hidden.

// what makes it trustworthy

Semantic caching that respects identity

The cache key is a SHA-256 hash of the resolved intent plus the caller's identity — not the raw question text. "What did Acme spend last month?" and "Show me Acme's spending for last month" hit the same cache entry. But two different callers never share a filtered result. 74–89% latency reduction on cache hits.

Audit envelope on every response

Every answer ships with a trust receipt: the compiled SQL, the proven join path, whether the cache was hit, which notes were retrieved, which route was taken, and how long it took. A downstream consumer never has to take "trust me" as the only option.

MCP integration

The gateway is exposed as a Model Context Protocol tool via FastMCP. Any MCP-aware client — Claude Code, Cursor, or a custom agent — can call it through the same compile → security → execute pipeline. It's not locked to this project's UI.

End-to-end observability

OpenTelemetry spans on every layer, exported to Langfuse. If tracing keys aren't configured, spans are still created — just not exported. Swapping to Datadog or your existing APM is a config change, not a code change.

// the hardest decision

Why the LLM should never write the query

The first version of this project had the LLM write SQL directly, then ran five checks before anything touched BigQuery. That catches dangerous queries. It doesn't catch plausible-but-wrong ones — a valid SELECT that joins on the wrong key, or aggregates at the wrong grain. Those pass every guardrail and return a number that looks fine.

The semantic gateway removes this entire class of errors. The LLM's job is reduced to intent extraction — naming a metric and its filters. The compiler owns the SQL. A hallucinated metric becomes a compile error, not a wrong answer. The trade-off is coverage: questions outside the certified glossary fall back to the original path (or are refused). That's a deliberate constraint, not a bug.

// what didn't work

A security-correct denial that crashed instead of returning empty

Three computed metrics used raw division — COUNTIF(...) / COUNT(*). When the security layer legitimately zeroed out matching rows (exactly what a denied query should look like), BigQuery raised a division-by-zero error instead of returning NULL. The query was correctly scoped to zero rows, but the formula didn't handle it.

Found by the golden eval set's own test case. Fixed with SAFE_DIVIDE. The lesson: a security layer that works correctly can still break downstream if the query assumes it will always have data.

Two refusal paths that skipped the audit trail

When the compiler refused a question or the security layer denied access, the response went straight to the user — bypassing the node that stamps the audit envelope. A denied request had no recorded reason for stopping, while every other terminal state did.

Fixed by routing both through the same halt node as everything else. If you have an audit trail, every exit path has to go through it — especially the error paths, because those are the ones someone will ask about later.

A guardrail that failed open (from the original agent)

Column validation looked up each table's columns from the schema context. A broken data structure made the lookup return empty every time. The code treated empty as "I don't know this table" and skipped the check. Every query passed, and the guardrail reported success.

A guardrail that skips when it's confused is worse than one that doesn't exist, because it reports success. Any check that can't complete has to fail closed.
