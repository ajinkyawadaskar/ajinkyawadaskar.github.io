Governed Text-to-SQL Agent with a Semantic Execution Gateway

Ask a question in plain English, get an answer backed by real data. The LLM never writes SQL — a deterministic compiler does. If the question doesn't map to a certified metric, it fails to compile instead of guessing.

Try the Demo GitHub Live API
// the problem

Most text-to-SQL tools let the LLM write the query directly. That works until it doesn't — and the failure mode is uniquely dangerous. The model doesn't crash or throw an error. It returns a number that looks right, reads right, and is completely wrong. A made-up column, a missing join, a filter that silently drops half the data. You get a confident answer with no way to know it's broken.

The first version of this project added guardrails — AST parsing, table allowlists, cost ceilings — to catch bad SQL after the model writes it. That works, but it's still reactive. The semantic execution gateway takes a different approach: don't let the LLM write SQL at all. It picks a metric from a certified list, and deterministic code compiles the query. A hallucinated metric becomes a name that doesn't resolve, not a query that runs and returns something plausible.

// architecture

The system has two paths. A structured path compiles SQL from a certified glossary — the LLM never writes a query. An unstructured path retrieves support notes from a vector store. A router decides which path (or both) a question needs, and a synthesis layer merges the results.

Where this sits

This is a Universal Semantic Layer — the same pattern behind Minerva, Cube, and dbt's Semantic Layer. Instead of letting each consumer (a dashboard, an agent, an API) re-derive business logic by querying raw tables, a single middleware owns the metric definitions, compiles governed queries, and serves consistent results to any surface.

Observability and the Audit Envelope are cross-cutting — they span every layer, not a step in the pipeline.

Each component, what it does, and how it scales

Router. Regex classifier that looks at question shape — does it ask for a number, a note, or both? Free, instant, and every decision traces to the exact pattern that fired. Production: swap for a lightweight LLM classifier when questions get ambiguous enough that keywords miss.

Intent Extraction. The LLM reads the question and emits a small JSON naming a certified measure, dimensions, and filters — validated against semantic_model.yaml. If the metric doesn't exist in the glossary, it's refused. The LLM never writes SQL. Production: expand the glossary as new metrics get certified; the compiler handles the rest.

Semantic Cache. SHA-256 of the resolved intent + caller identity. Two differently worded but identical questions hit the same entry. Two callers never share a filtered result. 74–89% latency reduction on hits. Production: move from SQLite to Redis; add TTL-based invalidation tied to data freshness.

Semantic Compiler. sqlglot expression builders turn the validated intent into SQL — graph traversal for joins, AST construction for predicates. No string concatenation anywhere. The compiler resolves join paths from an entity graph: when two valid routes exist, it picks the shortest path and fails at compile time if the path is ambiguous rather than guessing. Fan-out (one-to-many joins that inflate aggregates) is handled by the semantic model's grain declarations — the compiler knows which entity a measure is defined at and won't cross a grain boundary without an explicit aggregation. Production: add more join paths and aggregate functions to the semantic model as the warehouse grows; add schema-drift detection that validates the model against BigQuery's live metadata in CI.

Security Injection. After the LLM is done contributing anything, code walks the compiled AST and ANDs row-level predicates onto tables that carry a policy. An invalid identity raises an error outright — never a query that quietly returns zero rows. Production: wire to a real IAM provider instead of simulated tenant identities.

BigQuery Execution. The compiled, security-injected query runs against live BigQuery with the same guardrails as the original agent (cost ceiling, row cap). Production: add query queuing and priority lanes for expensive scans.

Vector Search (RAG path). For unstructured questions, retrieves relevant support notes from a LanceDB vector store. For stacked questions ("find customers who complained about billing, then show their revenue"), retrieval resolves who, then the compiler builds a precise query scoped to exactly those IDs. Production: replace synthetic notes with a real support-ticket corpus; add reranking.

Synthesis Layer. Merges outputs from the structured and unstructured paths into one attributed response. The LLM words the answer; the data behind it is deterministic. Production: add citation links back to source notes and query results.

Audit Envelope. Every response ships with a trust receipt — compiled SQL, proven join path, cache hit/miss, retrieved note IDs, route taken, and latency. A caller never has to take "trust me" as the only option. Production: pipe into a compliance dashboard for audit trails.

MCP Server. The gateway is exposed as a Model Context Protocol tool via FastMCP. Any MCP-aware client — not just this agent's UI — can call it through the same compile → security → guard → execute pipeline. Production: register as a standard tool in the organization's MCP registry.

Observability. OpenTelemetry spans on every layer, exported to Langfuse. init_tracing() with no keys is a documented no-op — spans are created, just not exported. Production: swap Langfuse for Datadog or your existing APM; it's a config change, not a code change.

// the hardest decision

Why the LLM should never write the query

The first version of this project had the LLM write SQL directly, then ran five checks before anything touched BigQuery. That catches dangerous queries. It doesn't catch plausible-but-wrong ones — a valid SELECT that joins on the wrong key, or aggregates at the wrong grain. Those pass every guardrail and return a number that looks fine.

The semantic gateway removes this entire class of errors. The LLM's job is reduced to intent extraction — naming a metric and its filters. The compiler owns the SQL. A hallucinated metric becomes a compile error, not a wrong answer. The trade-off is coverage: questions outside the certified glossary fall back to the original path (or are refused). That's a deliberate constraint, not a bug.

// what didn't work

A security-correct denial that crashed instead of returning empty

Three computed metrics used raw division — COUNTIF(...) / COUNT(*). When the security layer legitimately zeroed out matching rows (exactly what a denied query should look like), BigQuery raised a division-by-zero error instead of returning NULL. The query was correctly scoped to zero rows, but the formula didn't handle it.

Found by the golden eval set's own test case. Fixed with SAFE_DIVIDE. The lesson: a security layer that works correctly can still break downstream if the query assumes it will always have data.

Two refusal paths that skipped the audit trail

When the compiler refused a question or the security layer denied access, the response went straight to the user — bypassing the node that stamps the audit envelope. A denied request had no recorded reason for stopping, while every other terminal state did.

Fixed by routing both through the same halt node as everything else. If you have an audit trail, every exit path has to go through it — especially the error paths, because those are the ones someone will ask about later.

A guardrail that failed open (from the original agent)

Column validation looked up each table's columns from the schema context. A broken data structure made the lookup return empty every time. The code treated empty as "I don't know this table" and skipped the check. Every query passed, and the guardrail reported success.

A guardrail that skips when it's confused is worse than one that doesn't exist, because it reports success. Any check that can't complete has to fail closed.
