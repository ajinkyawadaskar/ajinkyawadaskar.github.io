Selected work

Two systems built around the same idea: the guardrail, not the model.

01 Credit Decision Explainer Live · complete

When a bank denies your loan, US law requires them to tell you the specific reasons. The tempting build is to hand the model's output to an LLM and ask for a letter — and it fails in a way that's genuinely hard to catch. In testing, one wrote that an applicant was denied partly for "limited employment history and recent credit inquiries." Neither was a factor. One of them isn't even in the dataset.

So the reasons are chosen by plain code from real SHAP attributions, the LLM only words them, and a checker verifies every sentence against that list before it ships. If the checker fires, the applicant gets blunt correct text instead.

The finding I didn't expect: the model wanted to deny people for paying their bills on time. Mathematically correct — that group defaulted 57% of the time — and completely unusable in a letter. Being traceable to real evidence isn't enough. It also has to be a reason you're legally allowed to give.

02 Data Analyst Agent Live · complete

Ask a question in plain English, get an answer from BigQuery. Every model writes competent SQL now, so that part is boring. The part nobody demos is what happens when it writes something wrong — inventing a column, reaching for a table you never exposed, scanning six gigabytes because it forgot a date filter.

You can ask a model nicely not to do that. It lowers the rate; it doesn't bound it. So every generated query gets parsed and checked against five rules that don't depend on the model cooperating — statement type on the syntax tree, table allowlist, column existence, row cap, and a dry-run cost ceiling. Fail any one and it doesn't run.

The cost check turned out to be the interesting one. COUNT(*) across 366 tables costs nothing — BigQuery answers it from metadata — while one unfiltered SELECT * is 5.8 GB. "Touches many tables" and "expensive" are different questions, and a guard built on the wrong one blocks free queries and lets costly ones through.

How I work

Three habits that show up in both projects.

The check can't depend on the model behaving

A prompt is a preference. A parser is a guarantee. In both projects the thing that says no is plain code with no model in it, which is the only reason there's anything to verify against. Same pattern in the debug agent I built at Ford: the LLM does diagnosis, thirteen deterministic checks decide what's actually wrong.

I publish the numbers that look bad

The credit model only catches 52% of risky applicants. The SQL agent answers 20% of questions correctly on a free-tier model. Both numbers are in the READMEs, next to what I'd do about them. A portfolio that only reports its wins isn't measuring anything — and the eval harness I built at Ford exists precisely to catch regressions before a cutover, which only works if you're honest about what it finds.

The failures are written down while they're still fresh

Each repo keeps a running log of what broke, written while it was still fresh. One entry is a test harness of mine that would have reported a hallucination that never happened — the worst kind of bug, because the obvious fix would have quietly destroyed the guarantee it was there to protect.
